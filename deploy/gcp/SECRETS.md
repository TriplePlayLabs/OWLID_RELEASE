# Secret management — OwlID GCP deploy

How secrets are stored, read by services, rotated, and audited.

## Where secrets live

All application secrets are in **Google Secret Manager** (`gcloud secrets`). Created and seeded by Terraform. Read by Cloud Run at container start via `secret_key_ref` env-var refs.

```
TF apply
  └─ random_password generates value (or static for some)
     └─ google_secret_manager_secret_version v1
        └─ lifecycle.ignore_changes = [secret_data]   ← value sticks after creation
           └─ Cloud Run env { value_source.secret_key_ref { version = "latest" } }
              └─ resolved on every cold-start (~3–8s)
```

**Plaintext is never in env vars or compose files.** The Cloud Run revision references the secret by ID + version; the actual value is fetched by the runtime SA at request time and injected into process env.

## What's stored

| Secret | Type | Generated by | Rotatable? |
|--------|------|-------------|------------|
| `db-password` | random hex 48 | TF `random_password.db` | yes — see Postgres section |
| `verification-db-url` | derived DSN | TF locals | rotates with `db-password` |
| `issuer-db-url` | derived DSN | TF locals | rotates with `db-password` |
| `admin-jwt-secret` | random hex 96 | TF `random_password.admin_jwt` | yes — invalidates sessions |
| `encryption-key` | random hex 64 | TF `random_password.encryption` | **NO** — encrypts at-rest data |
| `issuer-private-key` | random hex 64 | TF `random_password.issuer_pk` | yes — old creds keep verifying |
| `api-key-dev` | `owlid_sk_test_…` | TF | yes — rotate with redeploy |
| `midnight-sidecar-api-key` | random hex 64 | TF `random_password.sidecar_api_key` | yes — rotate sidecar + clients |
| `midnight-wallet-seed` | static (dev genesis) | TF static value | **NO** — losing it = losing on-chain state |

## Operations cheatsheet

| Task | Command |
|------|---------|
| Read value | `gcloud secrets versions access latest --secret=NAME --project=owlid-491411` |
| Add new version | `printf '%s' new-value \| gcloud secrets versions add NAME --data-file=- --project=owlid-491411` |
| List versions | `gcloud secrets versions list NAME --project=owlid-491411` |
| Disable a version | `gcloud secrets versions disable VERSION --secret=NAME` |
| Destroy a version | `gcloud secrets versions destroy VERSION --secret=NAME` |
| Force Cloud Run reload | `gcloud run services update SERVICE --region=europe-west1 --project=owlid-491411` |
| Audit access | Cloud Logging filter `protoPayload.serviceName="secretmanager.googleapis.com"` |

## Who can read

| Principal | Role | Source |
|-----------|------|--------|
| `owlid-run@owlid-491411.iam.gserviceaccount.com` | `roles/secretmanager.secretAccessor` | TF `iam.tf` |
| Project Owners (you) | `roles/owner` | manually granted |
| Anyone else | nothing | — |

To grant another principal access (read-only):
```sh
gcloud secrets add-iam-policy-binding NAME \
  --member='user:other@example.com' \
  --role='roles/secretmanager.secretAccessor' \
  --project=owlid-491411
```

## Rotation playbooks

### `db-password` (Postgres `owl` user)

```sh
NEW=$(openssl rand -hex 48)

# 1. Update Postgres
gcloud sql users set-password owl --instance=owlid-pg \
  --password="$NEW" --project=owlid-491411

# 2. Update db-password secret
printf '%s' "$NEW" | gcloud secrets versions add db-password --data-file=- --project=owlid-491411

# 3. Rebuild + push DSN secrets
SQL_CONN="owlid-491411:europe-west1:owlid-pg"
printf 'postgres://owl:%s@/verification?host=/cloudsql/%s' "$NEW" "$SQL_CONN" \
  | gcloud secrets versions add verification-db-url --data-file=- --project=owlid-491411
printf 'postgres://owl:%s@/issuer?host=/cloudsql/%s' "$NEW" "$SQL_CONN" \
  | gcloud secrets versions add issuer-db-url --data-file=- --project=owlid-491411

# 4. Roll Cloud Run services so they pick up `latest`
for svc in verification issuer; do
  gcloud run services update "$svc" --region=europe-west1 --project=owlid-491411
done
```

### `admin-jwt-secret`

```sh
printf '%s' "$(openssl rand -hex 96)" | gcloud secrets versions add admin-jwt-secret --data-file=- --project=owlid-491411
gcloud run services update verification --region=europe-west1 --project=owlid-491411
```
**Effect:** all admin sessions invalidated. Users must re-login.

### `issuer-private-key`

```sh
printf '%s' "$(openssl rand -hex 64)" | gcloud secrets versions add issuer-private-key --data-file=- --project=owlid-491411
gcloud run services update issuer --region=europe-west1 --project=owlid-491411
```
**Effect:** new credentials signed with new key. Existing credentials still verify (signature is pinned at issuance time). Holders/verifiers do not need to update.

### `api-key-dev`

```sh
printf 'owlid_sk_test_%s' "$(openssl rand -hex 24)" | gcloud secrets versions add api-key-dev --data-file=- --project=owlid-491411
for svc in verification verifier; do
  gcloud run services update "$svc" --region=europe-west1 --project=owlid-491411
done
```

### `midnight-sidecar-api-key`

```sh
printf '%s' "$(openssl rand -hex 64)" | gcloud secrets versions add midnight-sidecar-api-key --data-file=- --project=owlid-491411
for svc in sidecar verification issuer; do
  gcloud run services update "$svc" --region=europe-west1 --project=owlid-491411
done
```

### `encryption-key` — **DO NOT rotate**

This key encrypts at-rest credential data in Postgres (`credentials.encrypted_data`). Rotating it without re-encrypting all rows leaves data unreadable. If you must rotate:
1. Decrypt all rows with the old key
2. Re-encrypt with the new key
3. Add new key version
4. Roll verification

There is currently no migration helper. Treat as immutable for this dev sandbox.

### `midnight-wallet-seed` — **DO NOT rotate**

The seed derives the on-chain wallet address. Rotating it = abandoning the existing chain account (DUST balance, registered issuer position). If you do need a fresh wallet, plan it as a chain migration, not a secret rotation.

## Where TF stores the values

The Terraform state file in `gs://owlid-491411-tfstate/owlid/dev/default.tfstate` contains:
- `random_password.*.result` (plaintext)
- secret-version `secret_data` for those that don't have `lifecycle.ignore_changes` (the DB-URL secrets)

State protections:
- Bucket has uniform bucket-level access enabled
- Bucket versioning on (rollback past states)
- Only project Owners can read by default

For prod harden:
- Enable CMEK on the state bucket
- Restrict bucket IAM to a named SRE group
- Move secret values out of `random_password` and into a CI-time external KMS source

## Long-term hardening (not yet implemented)

- Pull secrets from **1Password / HashiCorp Vault** via CI step, never use TF random
- Use **SOPS**-encrypted YAML files in repo, decrypted at apply time
- Add **Cloud KMS auto-rotation** for the encryption key, with a re-encryption job
- Enable **VPC Service Controls** to constrain Secret Manager access to known networks
- Add a Cloud Build trigger that runs the rotation playbooks on a schedule
